# Working in this repo

## The remote

`origin` is `github.com/aiglassbox/the-last-colony`, and in this clone it is the
only remote. Its default branch is `main`. Ordinary work is pushed to a feature
branch on `origin` (for example `fix/…`); nothing is pushed straight to `main`.

Every other host is refused. The `pre-push` hook enforces exactly that and no
more, and it is local — a fresh clone will not have it, so the rule is the
instruction and the hook is only the reminder.

An earlier version of this file described two remotes — `origin` pointing at
`Anjali-Kore/recipe_project`, with aiglassbox as a second target you had to name
explicitly, and a shared-history note about a common ancestor between them. This
clone is not wired that way: there is one remote and it is aiglassbox. Add and
name any second remote before a task relies on it.

## Two packages, one repo

The app is at the root: Next.js, `src/`, deployed as the website.

`pipeline/` is a separate npm package — the retrieval engine that embeds the
199-recipe corpus into Pinecone and searches it. Its own `package.json`, its own
`node_modules`, its own `.env`, its own tsconfig. Run its commands from inside
`pipeline/`; run the app's from the root. The root tsconfig and eslint config
both exclude it on purpose.

See `pipeline/ARCHITECTURE.md` for how retrieval works and what has been measured.

## This is not the Next.js you know

Next 16 with Turbopack. APIs and conventions differ from older versions — read
the relevant guide in `node_modules/next/dist/docs/` before writing routing,
metadata or route-handler code. In particular: `params` and `searchParams` are
promises, and `PageProps<'/route'>` / `RouteContext<'/route'>` are global
helpers generated by `next dev` / `next build` / `next typegen`.

## The rules that are not style preferences

1. **The model never writes a citation.** Ingredient table, method, source
   strip, provenance badge, contested points, Then/Now diff and the share image
   all render from the retrieved record. If you find yourself adding a beat
   where the model lists sources, stop.
2. **An unverified record cannot claim `ATTESTED`**, cannot carry
   original-language text, and has its locus withheld from the model. The
   validator enforces this; do not add an escape hatch. The model must not name
   a provenance class in prose either — the badge renders it from the record,
   and `guards.ts` logs `[provenance-leak]` when a completion does. A model has
   already been caught calling an unverified record "ATTESTED"; assume the next
   one will try.
3. **Retrieval declines rather than guesses.** Below threshold, on an unknown
   token, or on ambiguity, return empty and log the gap. Never fall back to the
   nearest neighbour — and when a corpus miss hands the model vector candidates,
   `mayPromoteCandidate` withholds any whose name shares no token with the query,
   so a `MODE: RESTORE` can never promote an unrelated neighbour onto the card.
   A corpus hit that turns out to be a modern namesake of the record (sabudana
   khichdi vs the ancient Kṛsara) is withdrawn the same way, via `§NO_ANCESTOR§`.
4. **No health claims anywhere** — corpus text, prompt or UI. Comparative
   nutrition on a named axis only.
5. **No communal or ethnic framing.** Colonial economic policy is documented
   history. Attributing dietary change to a religious or ethnic community is
   not, and the prompt declines it.

## Reading the numbers

`/kitchen` is the analytics dashboard, behind one shared password in
`KITCHEN_PASSWORD`. Unset, the route and its API both 404 — the same fail-closed
posture `/api/email-report` has, and for the same reason.

Two sources feed it and they answer different questions.

`conversations` is the thread mirror and it starts at the first keystroke, so
every figure drawn from it counts people who **typed**. It is a floor on
traffic, never a measure of it. It also undercounts over long windows: the
mirror is replace-by-device and a browser keeps thirty threads, so a heavy
device's older rows are deleted from the server when it syncs.

`analytics_events` is the event log, and it is what `track()` writes to now in
addition to stdout. That is the half that knows about arrivals, campaign
markers and shares. It starts at the deploy that added it; nothing before that
was ever stored and none of it can be back-filled.

Two things to keep true when touching either:

1. **The dashboard must not appear in its own numbers.** `VisitTracker` skips
   any path under `/kitchen`. It lives in the root layout, so without that
   guard every look at the graphs writes a row into the graphs.
2. **Painted neighbours must be palette neighbours.** The chart colours in
   `lib/dash/tokens.ts` were searched and validated on their *adjacent* pairs,
   so a stacked bar that assigns slots out of order throws the guarantee away.
   Re-run the check before changing any of them:

   ```bash
   node <dataviz-skill>/scripts/validate_palette.js "#bd8a0a,#ab575e,#7762d6,#33a5b2,#d15d15,#bc59a3" --mode dark --surface "#182610"
   ```

## Before you push

```bash
npm run check   # corpus validation + the hand-checked retrieval queries +
                # the semantic-promotion guard + the routing checks
npm run lint
npm run build
```

A **wrong** retrieval answer fails the harness and should fail the review too.
A miss is a corpus gap; a wrong ancestor is a campaign risk.

## Editing the system prompt

`BRIEF_PROMPT` in `src/lib/model/system-prompt.ts` is Part 2 of the campaign
brief, verbatim, so that drift is a one-line diff. Put additions in
`OUTPUT_CONTRACT` beneath it rather than editing the brief text in place.
